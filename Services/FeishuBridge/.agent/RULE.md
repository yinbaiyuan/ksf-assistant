# 飞书桥本地规则

本文件记录飞书桥项目的本地协作规则。若本文件与用户明确指令冲突，优先执行用户指令；若与项目技术规格冲突，先指出冲突，再按更保守的安全边界处理。

## 项目定位

飞书桥是一个本机常驻 Node.js 服务，用来连接飞书自建机器人、官方 SDK 单一入站长连接、`lark-cli` 飞书 API 客户端和本机 Codex。

它当前负责：

- 通过 `@larksuiteoapi/node-sdk` 的单一长连接接收机器人消息与卡片回调事件。
- 做用户、群聊和路由权限判断。
- 把飞书消息分流到命令模式、任务模式和说话模式。
- 通过 `codex app-server` / `codex app-server proxy` 调用 Codex。
- 把 Codex 的回复、任务状态和错误回传飞书。
- 写入 JSONL 日志和项目内 Markdown 审计页。
- 所有飞书 API 读取、写入、消息发送和文档相关 OpenAPI 调用统一通过 `lark-cli` 执行；官方 SDK 只承担入站事件传输。

它不是业务系统，不承载上层业务对象生命周期。

## 职责边界

飞书桥负责：

- 飞书消息通道。
- 飞书用户、群聊和路由权限判断。
- 飞书消息去重、分段发送和回传。
- Codex app-server 调用链路。
- JSONL 运行日志。
- 项目内人类可读审计页。
- 通用追踪信息透传。
- 明确格式文本的轻量结构化解析。
- 文档创建、编辑请求的通用任务编排、状态、日志和审计。

飞书桥不负责：

- HAPOS 状态流转。
- HAPOS 或其他上层系统的审查裁决。
- 上层系统的业务对象生命周期。
- 复杂业务判断。
- 绕过 docbox 版本保护更新既有飞书文档。
- 直接替 Codex 执行业务语义层面的文档改写判断。
- 绕过权限向任意飞书用户或群主动发消息。

## 架构演进原则

新增能力必须优先抽象为通用消息通道、通用 `trace`、通用 parser 或通用 worker。不要为了 HAPOS 或某个具体业务写死特判逻辑。

如果一个需求看起来需要特判，先判断它是否暴露了更通用的概念、状态、策略、关系或扩展点。优先通过清晰模块职责、通用字段、配置或策略解决；只有在业务确实是一次性例外且成本可控时，才接受局部特判，并记录原因和清理条件。

当前项目可以先保持单文件主程序，但新增复杂子系统时应收敛为清晰函数区块，避免把业务规则散落在多个 `if/else` 分支中。

## 安全规则

真实 App Secret、token、open_id 白名单、chat_id 白名单等敏感信息不得写入文档、代码或示例。

主动出站不限制目标白名单，但必须同时满足：`FEISHU_OUTBOUND_ENABLED=true`、调用方本轮明确提供动作/目标/正文、通过 outbox、保留 dry-run、去重、脱敏和审计。入站白名单继续独立生效，不能因出站放开而扩大谁可以操控机器人。

涉及主动发飞书消息的能力，必须优先支持 dry-run。真实发送前应先用 dry-run 验证日志、审计、权限和去重行为。

写入飞书文档、移动 Wiki 节点、修改协作者权限属于高影响操作。除非用户本轮明确要求并给出目标，否则只给方案和待确认清单。

高影响飞书文档编辑必须由 Codex 先读取目标文档、说明拟改动和风险，再在任务授权边界内执行。飞书桥不维护桥内预览/确认状态机。

群聊上线前应限定 chat_id；群聊默认只开放低风险命令，不开放高影响写入能力。

## 日志与审计规则

`logs/*.jsonl` 是机器可读运行事实，项目内审计页是人类可读摘要。两者用途不同，不应互相替代。

默认不读取或修改 `logs/` 中历史运行数据，除非任务明确要求排查日志。

新增日志字段必须保持向后兼容。已有 JSONL 消费方不应因为新增字段而失效。

错误、权限拒绝、重复消息、dry-run、分段发送和 Codex 任务状态都应留下可追溯记录。

技术规格以 `docs/feishu-bridge-technical-spec.md` 为准。历史接入背景以 `docs/feishu-codex-integration.md` 为准。新增环境变量、消息模式、日志格式、权限边界时，必须同步更新技术规格。

## 出站能力边界

飞书桥不知道 HAPOS 的存在。其他系统可通过通用 `trace` 字段传递追踪信息，飞书桥只透传和记录 `trace`，不理解业务含义。

审查相关能力只做消息发送、入站记录、追踪码识别和轻量 key-value 解析。审查规则、审查结论采纳、任务状态流转由上层系统负责。

若实现出站 outbox 能力，其他项目只应写入 outbox，不直接调用飞书发送 API。

若实现文档任务 docbox 能力，其他项目只应写入 docbox，不直接调用飞书文档 OpenAPI。飞书桥只负责编排、状态、审计和唤醒；文档相关能力统一通过固定 `lark-cli` 适配器执行。创建文档使用 `docs +create → fetch`，正文只走 stdin，不启动自由 Codex 任务；更新既有文档由飞书桥执行基础版本保护更新。

docbox 编辑既有飞书文档时，必须先创建飞书官方文档版本，再执行编辑。版本创建失败时不得继续写入目标文档。除非后续另行设计高权限豁免字段，否则 `update_document` 默认采用 `versionPolicy: "official_before_update"`。docx 官方版本管理固定使用 `lark-cli api` 调用 raw API `/open-apis/drive/v1/files/:file_token/versions`，不要使用 `drive +version-history` shortcut 作为 docx 版本依据。

## 开发规则

优先保持项目简单。不要在未确认边界前引入数据库、HTTP API、队列、复杂框架或长期后台子系统。

新增环境变量必须同步更新 `.env.example` 和 `docs/feishu-bridge-technical-spec.md`。

`@larksuiteoapi/node-sdk` 只允许用于 `lib/official-event-adapter.js` 的单一入站长连接，不得用其 Client API 增加飞书读取、写入或消息发送，也不得并行启动第二个事件消费者。需要新增飞书 API 时，优先使用 `lark-cli` 已有快捷命令；没有快捷命令时使用 `lark-cli api METHOD /open-apis/... --format json`，参数必须使用数组传参，不得 shell 拼接。

当前官方 SDK 只分发 `event` 数据帧，`card.action.trigger` 使用隔离在 `lib/official-event-adapter.js` 的窄兼容覆盖。升级 SDK 时必须验证该内部钩子；官方实现原生支持 `card` 数据帧后应删除兼容覆盖，并保持单连接和既有业务处理器不变。

lark-cli 调用应优先收敛到 `lib/lark-cli-runner.js`，避免在 `bot-bridge.js` 中散落新的飞书命令拼装。

新增命令模式能力时，应同时说明触发方式、权限边界、日志行为和审计输出。

新增 docbox 请求类型时，应同时说明请求 schema、状态枚举、dry-run 行为、Codex 任务边界和失败处理。

新增 Codex 调用能力时，应保持 `codex app-server proxy` 优先、独立 app-server 回退的现有策略，除非有明确理由调整。

## 验证规则

修改 `bot-bridge.js` 后至少运行：

```bash
node --check bot-bridge.js
```

涉及主动发消息时，验证顺序必须是：

1. dry-run。
2. 用户明确授权的目标真实发送。
3. 飞书平台不可达或权限不足场景。
4. 去重场景。
5. 日志和项目内审计页检查。

涉及 Codex 任务链路时，应验证任务创建、任务完成、任务失败、继续任务和默认说话模式。

涉及 docbox 文档任务时，应验证 create 任务创建、update 版本保护更新、dry-run、source 拒绝、重复 ID、坏 JSON、半行跳过、版本创建失败、文档更新失败和审计记录。
