# 用户身份写操作桌面批准门禁

状态：`0.11.0-preview.3` 候选，自动化与本机验收分开记录；未通过真实人工点击验收前不视为完成切换验收。完整能力契约见 [受管飞书执行契约](managed-feishu-capabilities.md)。

## 权威与数据流

- `Core/internal/usercommand` 固定审查 lark-cli 1.0.93 命令语义，解析明确身份，冻结 stdin、正文和附件，生成精确摘要。未知命令、覆盖授权上下文、动态隐式写入与无法确定的作用范围均拒绝，不按 HTTP 方法猜测读写。
- `Core/internal/userapproval` 是独立单次批准状态机，不属于任务卡片 integration 或 KSF 任务运行态。`Core/internal/service/user_approval.go` 独立重验官方身份、动作与现有能力策略，并绑定策略摘要；Core 不信任 caller 的 read/approved 声明。
- 受管 `ksfas-lark` 通过本机私有连接申请；飞书服务在真实执行器处通过现有 Core—飞书私有协议申请。兼容 CLI 与通用动作没有豁免批准；文档工作箱已退役，Doc/Wiki Skill 使用受管 ksfas-lark。机器人操作及受审查的 user 纯读取不增加桌面依赖。
- `/request`、`/status`、`/consume`、`/result`、`/cancel` 绑定同一连接和 Core 代次。`/poll` 与 `/decide` 仅宿主匿名管道暴露，不通过本机 CLI、飞书回调或 Windows renderer 暴露。
- macOS AppKit 与 Windows Electron 主进程展示原生窗口，默认拒绝。用户身份、应用、动作、目标、完整正文/修改参数与附件摘要先呈现；来源未验证不能被 caller 改成可信任务。批准不能存为可转用凭证。

## 生命周期与原有策略

待批最多十项，每项最长五分钟。宿主轮询同时提供可交互心跳；心跳失联、锁屏、拒绝、关闭、取消、请求方断开、退出或重启使未执行请求失效。不能依靠重新连接复用批准。执行前重验摘要、实际官方身份和策略，原子消费一次；开始执行后断线或无明确结果记为 unknown，不自动重放。

原有 disabled 能力仍拒绝。confirm_each 对受管 user 写采用同一次桌面批准，不允许 challenge、explicitAuthorization 或功能开关冒充桌面批准。固定适配器仅在批准后生成受支持的官方确认选项，不根据错误文字追加参数重试。

批准后、消费前，受管执行器获得跨进程授权执行锁，再重验身份并执行；应用的配置、登录、注销也使用同一锁，不能在已批准操作的实际执行窗口切换身份。锁只在批准后获取，竞争时明确报忙，不持锁等待用户点击。Core 的策略重验和批准消费与原有策略保存锁互斥；批准消费之后已开始的操作不因后续改策略而重放。

批准内容仅在内存中等待展示。`user-approval-audit-v1/` 私有审计只记录随机请求 ID、摘要、状态和时间；不存实际身份标识、目标、正文、附件副本或秘密。业务队列继续由原有组件拥有，不复制或恢复旧队列。

## 明确限制

- 门禁仅覆盖 KSFAssistant 受管入口；不是同用户权限的 CLI/API 全机隔离，也不能证明普通弹框必然由真人点击。本轮不增加生物识别、沙箱、常驻网络代理或额外调度服务。
- 命令审查表不是全部飞书业务 API 的新实现；未审查命令明确不支持，不能改用其他身份或绕过受管命令。读取并标记已读不算纯读取。
- 受管官方入口以固定发行版的 250 个类型化命令、526 个快捷命令及精确原生 API 契约为审查母集；实际支持与限制查询 `ksfas-lark managed capabilities --json`。权限变更和副作用读取按完整写入影响审查，不按名称放行；动态脚本和未知复合操作拒绝。
- 冻结兼容入口保留原公共能力范围，参数和真实执行进入同一描述、冻结与策略链路；不把调用者自称 read/bot 当依据，不因能力补全扩大旧业务目录。
- 私有 IPC 传输设有限定大小，超限请求拒绝而不是截断内容取得宽泛批准。动态资源导入和未限定复合动作不放行。
- 文档更新中的“创建版本”与“修改正文”是两个真实远端写动作，分别批准；后一个被拒绝时前一个已经产生的事实不回滚、不重放。UI 分别显示各动作，不声称业务事务原子性。
- 原有未知事件、旧卡片故障不属于本次修复，不清理、不重放。Windows 自动化和交叉编译不等于实机验证。

## 验收与回退

自动化仅使用隔离数据和假 CLI/原生对话框替身，不执行真实飞书写入。必验身份/命令矩阵、冻结输入、重复消费、策略/身份变化、连接取消、重启、审计隐私、宿主专属接口与进程退出。实际批准按钮必须由用户亲自点击。

本机由用户指定最小测试目标：读取不弹框；写入拒绝无副作用；批准后恰好一次；关闭/超时无执行；应用未运行时 user 写失败；等待批准期间退出安全。安装保留前版，回退只切换应用与未修改的受管 Skills，不恢复旧业务队列，不删除已经产生的业务事实。不提交、推送、公证或公开发布。

## macOS 精简批准窗口

macOS 使用 440pt 原生窗口，按动作、完整目标、身份/应用、来源、操作内容、附件和详情分层。内容按原文展示，可滚动或展开；缺少历史正文时不生成虚构的前后对比。附件只在存在时展示名称与大小，完整参数、哈希和失效时间保留在“查看详情”。长目标/正文可滚动，底部按钮始终可达。默认不设置批准快捷键，Return、Esc 与关闭窗口都取消；查看详情不提交决定。

Core 在解析冻结参数时生成可选 `preview`（`content`、`confirmLabel`、`destructive`），保持 poll schemaVersion=1。预览仅排除另行展示的目标和附件技术信息，JSON 正文/权限范围及其他非控制参数保持完整；不从拼接文本中删行、不调用模型摘要、不改变执行或授权规则。`title` 在详情中保留原审查描述，`action` 使用已审查的中文动作名；未映射操作保留明确命令名。破坏性颜色取最终审查风险，包括覆盖正文的附加影响。旧请求没有 preview 时显示完整 content，不猜测删减。Windows 校验新增可选字段，仍使用原有原生分页批准流程。

验证：`bash scripts/render-user-approval.sh` 仅编译界面与隔离样例，检查浅/深色、短/长正文、删除、完整详情、长目标及按钮回调；不会连接 Core、读取凭证或执行真实批准。真实写入门禁仍需人工点击验收。
