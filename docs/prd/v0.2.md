# KSFAssistant v0.2 product rules

## Goal

Turn the existing quota popover into a compact workbench for every KSF project, without weakening the stable menu-bar quota/task signal or making the entire panel scroll.

## Project catalog and workset

- The only project catalog source is `10项目/*/项目记忆卡.md`, interpreted by KSF and exported as `ksf-panel-catalog-v1`.
- Only active project cards enter the current catalog. Pinned cards that disappear or become archived remain as unavailable placeholders until unpinned.
- The home project area is a vertical detail list containing the union of pinned projects and projects bound to currently running or waiting tasks, plus one runtime-only `无项目` Cell whenever active top-level tasks cannot resolve either assignment source. Merely existing in the active catalog does not add a project to the home list.
- Put `无项目` first so it cannot fall beyond the initial four Cells, then pinned projects and current-task projects. Record a normal project's position when it first enters the list and preserve that relative position across task-status, Token, and latest-activity updates, panel reopenings, temporary removal/re-entry, and app restarts. A new project appends to its group; only an explicit pin or unpin moves it between the pinned and unpinned groups. The synthetic Cell and its task order remain in memory only.
- The first four workset projects appear by default. When more than four exist, a bottom `更多` control expands the complete workset inside a bounded native vertical scroll region; `收起` restores the compact state. Every panel opening returns to the home page and the four-row state.
- The restored project-list icon opens the complete active KSF catalog plus unavailable pinned placeholders as one continuous list without pagination; `无项目` never enters this catalog. Every row renders at once in a natural-height stack. The page has no internal scroll view, lazy stack, fixed-height frame, viewport estimate, or scroller gutter; the Popover height follows catalog size. Each available row shows project identity, a catalog-only archive-task control immediately before an independent pin control, followed by the same `累计 / 今日` Token values and five project actions as its home container. It does not show `已固定`, `项目库`, aggregate task-state copy, task rows, or task routes.

## Assignment and route projection

- A top-level desktop task belongs to a project only when a current `ksf-task-project-projection-v1` says so or its `cwd` exactly equals one declared engineering root. Parent directories, descendants, names, titles, and conversational text never create an inferred assignment.
- A running or waiting top-level task that cannot resolve to an active catalog project remains visible under `无项目`. This is a display fallback, not a project assignment: it creates no KSF object, project Token attribution, pin state, project memory, folder, engineering, launch, or new-task action.
- The verified route wrapper publishes only after the pure `verified-route-projection-v6` succeeds, the app has enabled the bridge, `CODEX_THREAD_ID` exists, and exactly one project-memory root card is present.
- The projection contains a local HMAC task key, relative project card, work category, jobs, abilities, dispatchable Skills, binding/observation timestamps, and receipt hash. It is display-only and never changes KSF authority, route receipts, task-support traces, evidence, or validation states.
- A home project is a container for every active top-level task assigned to it. It never selects a representative task and never generates a task summary. Each task uses its original `thread/list` name and its own projected route: category and main job on the second line, named abilities plus dispatchable-Skill count on the third line, and the complete grouped route in its inline disclosure. Missing values display `未命名任务` and `未绑定 KSF 路由`.
- Deduplicate task observations by `hostID + threadID`. The App Server catalog plus conservative project assignment supplies local top-level candidates for proactive desktop owner discovery; window-following events are only discovery hints, and an unfollow does not remove a task until its runtime state is no longer active or waiting. Initialize a project's task order by creation time, then keep first-seen order for the app session: state, route, Token, and update-time changes do not move rows, and newly observed tasks append. Completed tasks disappear promptly.
- Waiting states are mutually exclusive from running and use this priority: permission/command approval as `待批准`, incomplete `planImplementation` as `待确认计划`, user question/selection/information requests as `待回复`, and any remaining pending action request as `待处理`.
- Task identity, original name, status, and row order are memory-only. They never enter Application Support, UserDefaults, logs, or the KSF projection.

## Project Token accounting

- Accounting begins when the local bridge is enabled and a task receives a verified project binding. No historical project attribution is guessed.
- Read-only thread metadata comes from Codex App Server `thread/list`; local session files contribute only timestamps, session/record ownership, parent relationships, and request-level usage / legacy cumulative counters.
- Count request usage or legacy positive counter deltas in the binding active at the sample timestamp. A later project binding splits subsequent deltas. Child-agent threads inherit the nearest ancestor binding timeline. Counters remain independent; project accounting uses the same provenance-aware session deltas as local daily accounting, so a fork's copied history is a baseline, not new project usage.
- `项目累计 Token` covers all locally observable bound intervals; `项目今日 Token` uses the Mac's natural calendar day.
- Missing local logs, including remote tasks, mark coverage incomplete. Zero is shown only when the locally observable scope is complete; an unavailable or incomplete empty scope is labeled instead.
- Cache only normalized per-project totals, date boundary, coverage flag, uncounted count, and tracking start. Never cache thread IDs, titles, raw events, or conversation content.

## Project actions

- `新增任务` prepares a resumable draft in a dedicated Codex App Server process: `thread/start → thread/name/set → thread/inject_items`. Only factual initialization context (task name and working directory) is injected, since current Codex cannot resume an empty reserved thread in another process. Core closes and waits for the writer to exit, then the platform host opens the exact task. Core waits up to 10 seconds for Desktop ownership on an isolated control connection and sends the actual bootstrap prompt as one normal text input through `thread-follower-start-turn` v2. This produces a persistent first user message and a visible assistant reply. The independent process never invokes the model. First-turn submission is bound to the prepared thread, working directory and prompt, expires after 10 minutes, and is consumed before IPC dispatch. Timeouts, rejections and repeated host calls never replay the instruction. A failed handoff is reported as a created task whose startup could not be confirmed. Model and permission settings are inherited from Desktop. The bootstrap input contains the selected project name and memory-card path, requests context preparation only, prohibits concrete work, file changes or an implementation plan, and asks for a short readiness response.
- Git engineering mappings never replace the KSF owner root. The new-task control is therefore always a direct action for no-Git, single-Git, and multi-Git projects; multi-root selection remains only on the Git-folder control.
- The bootstrap turn inherits the visible task's thread settings and does not send approval, sandbox, model, or reasoning overrides. The user's normal Codex defaults therefore remain available after the preparation turn.
- The bootstrap prompt and returned raw thread ID are never written to app cache, UserDefaults, or logs. The prompt exists in the user-created Codex task by design. A missing directory or context entry blocks creation locally; a preparation or open failure stays in that project container, and no Shell fallback is used.
- `归档项目` exists only in the complete project catalog. Clicking its `archivebox` control creates the named task `项目名 · 归档项目` in the configured KSF root, opens that exact task, and submits a compact prompt containing the exact project-memory card plus instructions to load KSF context, check archive prerequisites and unresolved work, request any required user authorization, and otherwise complete and report the archive. The App never changes project status or moves files directly, and the home project container has no archive control.
- `KSF` opens the selected KSF project directory. `Git 工程` opens its mapped engineering root in Finder. A single mapping opens immediately; multiple mappings use a menu with the exact active-task `cwd` match first.
- Project launch recognizes only `start.sh` directly inside the KSF project directory exported by the catalog. Git roots, project names, manifests, nested scripts, and other conventional files never create launch actions.
- During project refresh, `start.sh` must be a current-user-owned regular file, not a symbolic link, have owner execution permission, and reject group/other write permission. A missing file is an ordinary disabled state; an unsafe file produces a concise project-sync warning.
- The home Cell exposes one direct `play.fill` control when the script is valid and a disabled `play.slash` otherwise. A click revalidates the same file to prevent replacement after refresh, opens visible Terminal, changes to the KSF project directory, executes `start.sh`, reports its exit status, and leaves the shell open.
- Launch never runs in the background and accepts no action menu, arguments, environment injection, engineering-root override, or Shell fallback.

## Interface

- Keep the status label and global task-count rules from v0.1 unchanged.
- The popover is 336pt wide with content-driven height. Home gives the project workset its natural height and never wraps it in an internal scroll view or fixed-height frame; task disclosure and `更多` grow the Popover itself. The local Token-history page and complete project catalog also use natural content height without internal scrolling. Settings contains no scroll view, tab view, or sidebar.
- Home order: header, general quota, account/local Token activity, then the KSF project heading and vertical project containers.
- Each real-project container shows its name, aggregate task status, every real active task, project lifetime/today Token, new-task shortcut, folders, direct project-memory access, and the single project-directory `start.sh` launch control. The `无项目` container shows only its title, aggregate status, task rows, and local open failures. There is no project-detail page or selected-project state. The running `play.fill` count is always present, including `0`; the pin icon alone conveys pinned state and `已固定` never replaces the running count.
- Every task row is a three-line disclosure. Line one contains status symbol, original name, explicit state, a separate icon-only Codex-open control, and disclosure control; line two contains `工作类别 · 主岗位`; line three names the task's abilities and shows its dispatchable-Skill count. Clicking the task body expands or collapses its complete route in place, with only one task expanded across home. The complete route distinguishes main and collaborating jobs, groups abilities by `job_id`, groups dispatchable Skills by `ability_id`, includes validation and Skill-stage labels, and preserves unmatched entries in explicit fallback groups. Only the separate open control uses `codex://threads/{percent-encoded-task-id}`. A local open failure appears only in that project container and never falls back to Shell or conversation inspection.
- The first four projects are included by default, with all their tasks and without an internal height limit. `更多` includes projects beyond four in the same natural-height workset. No scrollbar gutter is reserved on the home page.
- The complete project catalog remains compact but action-capable: project name, archive-task control, and pin on line one, then the shared home-project Token/action Footer on line two. The archive control is immediately before pin and never appears on home. Its rows do not navigate or expose selected state, aggregate task-state copy, task names, or task routes. Unavailable pinned placeholders show only their name, unavailable state, and unpin control.
- Settings adds KSF directory status/reselection to login launch, quota-reset notifications, and the icon-plus-`退出` destructive action. There is no refresh button; opening, wake, and existing timers refresh data.
- Failures stay local to their region. KSF or project metadata failures do not change quota/task availability; quota failures do not remove the project catalog.

## Acceptance

- The live KSF export returns 15 current active projects, including no-Git, single-Git, and multi-Git cases, without the app parsing project Markdown.
- The current verified task appears under its bound KSF project even when its `cwd` is the KSF root; an unrelated KSF-root task without projection appears under `无项目` without gaining project attribution or Token accounting.
- Multiple running and waiting tasks under one project retain their own names, waiting reasons, and KSF routes; duplicate desktop windows do not duplicate rows or counts. Newly arriving tasks append without reordering existing rows.
- Project switching, stable pinned-first ordering, activity updates without row movement, unavailable pins, exact `cwd`, child inheritance, binding transitions, day boundaries, and missing logs are covered by deterministic tests.
- Start-script validation covers missing, valid, non-executable, group/world-writable, symbolic-link, refresh-to-click replacement, and visible Terminal execution failures.
- New-task tests verify factual initialization context without a hidden bootstrap instruction or background generation, isolation from the long-lived account/Feishu process, process-exit acknowledgement, delayed Desktop ownership, a targeted first-turn request with one exact visible user input and no settings overrides, cancellation cleanup, and rejection of mismatched, expired or repeated submission. Live smoke validation must confirm another process can resume the prepared task and Desktop retains one canonical user message and an actual final response.
- Archive-task tests verify the catalog-only button order and scope, explicit `项目名 · 归档项目` naming, KSF-root ownership, exact project-card context, archive-prerequisite and authorization language, omission of engineering-root duplication, targeted foreground submission, and the boundary that the App itself performs no archive mutation.
- The default home includes at most four project containers but never truncates their task rows; when present, `无项目` is the first included container. The home project workset uses natural height without an internal scrollbar. `更多` includes the remaining pinned/current-task projects by growing the Popover. The complete catalog contains every real project on one natural-height secondary page, excludes `无项目`, and has no pagination, lazy loading, internal scrollbar, or fixed height.
- Application Support contains no raw task ID, task title, prompt, conversation content, full route receipt, credential, or raw JSONL event.
- Direct tests, universal2 release build, Info.plist validation, ad-hoc signature, live App Server read, desktop IPC probe, and installed-app launch all pass.
