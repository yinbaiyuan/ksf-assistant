# Codex Usage Bar v0.2 product rules

## Goal

Turn the existing quota popover into a compact workbench for every KSF project, without weakening the stable menu-bar quota/task signal or making the entire panel scroll.

## Project catalog and selection

- The only project catalog source is `10项目/*/项目记忆卡.md`, interpreted by KSF and exported as `ksf-panel-catalog-v1`.
- Only active project cards enter the current catalog. Pinned cards that disappear or become archived remain as unavailable placeholders until unpinned.
- The home project area is a vertical detail list containing only the union of pinned projects and projects bound to currently running or waiting tasks. Merely existing in the active catalog or being the last selected project does not add a project to the home list.
- Put pinned projects first and current-task projects below them. Record a project's position when it first enters the list and preserve that relative position across task-status, Token, and latest-activity updates, panel reopenings, temporary removal/re-entry, and app restarts. A new project appends to its group; only an explicit pin or unpin moves it between the pinned and unpinned groups.
- The first four workset projects appear by default. When more than four exist, a bottom `更多` control expands the complete workset inside a bounded native vertical scroll region; `收起` restores the compact state. Every panel opening returns to the home page and the four-row state.
- The restored project-list icon opens the complete active KSF catalog plus unavailable pinned placeholders as one continuous list without pagination. The list uses natural height when short and a bounded vertical scroll region when long. Its overlay scroll indicator has a permanent trailing safe area, so indicator visibility never changes row width. Opening a catalog project does not make it part of the home workset unless it is pinned or has a current task.

## Assignment and route projection

- A top-level desktop task belongs to a project only when a current `ksf-task-project-projection-v1` says so or its `cwd` exactly equals one declared engineering root. Parent directories, descendants, names, titles, and conversational text never create an inferred assignment.
- The verified route wrapper publishes only after the pure `verified-route-projection-v6` succeeds, the app has enabled the bridge, `CODEX_THREAD_ID` exists, and exactly one project-memory root card is present.
- The projection contains a local HMAC task key, relative project card, work category, jobs, abilities, dispatchable Skills, binding/observation timestamps, and receipt hash. It is display-only and never changes KSF authority, route receipts, task-support traces, evidence, or validation states.
- A home project is a container for every active top-level task assigned to it. It never selects a representative task and never generates a task summary. Each task uses its original `thread/list` name and its own projected route line `工作类别 · 主岗位 · N 基本功 · N Skill`; missing values display `未命名任务` and `未绑定 KSF 路由`.
- Deduplicate task observations by `hostID + threadID`. The App Server catalog plus conservative project assignment supplies local top-level candidates for proactive desktop owner discovery; window-following events are only discovery hints, and an unfollow does not remove a task until its runtime state is no longer active or waiting. Initialize a project's task order by creation time, then keep first-seen order for the app session: state, route, Token, and update-time changes do not move rows, and newly observed tasks append. Completed tasks disappear promptly.
- Waiting states are mutually exclusive from running and use this priority: permission/command approval as `待批准`, incomplete `planImplementation` as `待确认计划`, user question/selection/information requests as `待回复`, and any remaining pending action request as `待处理`.
- Task identity, original name, status, and row order are memory-only. They never enter Application Support, UserDefaults, logs, or the KSF projection.

## Project Token accounting

- Accounting begins when the local bridge is enabled and a task receives a verified project binding. No historical project attribution is guessed.
- Read-only thread metadata comes from Codex App Server `thread/list`; local session files contribute only timestamps, parent relationships, and `token_count` cumulative counters.
- Count positive counter deltas in the binding active at the sample timestamp. A later project binding splits subsequent deltas. Child-agent threads inherit the nearest ancestor binding timeline.
- `项目累计 Token` covers all locally observable bound intervals; `项目今日 Token` uses the Mac's natural calendar day.
- Missing local logs, including remote tasks, mark coverage incomplete. Zero is shown only when the locally observable scope is complete; an unavailable or incomplete empty scope is labeled instead.
- Cache only normalized per-project totals, date boundary, coverage flag, uncounted count, and tracking start. Never cache thread IDs, titles, raw events, or conversation content.

## Project actions

- `新增任务` creates an idle Codex task through the documented App Server `thread/start` and sets its visible name to `项目名 · 新任务` through `thread/name/set`. The App then opens that exact task, waits for the visible Codex Desktop window to follow it, and submits one bootstrap turn directly to the client ID carried by that following broadcast through desktop `thread-follower-start-turn` v2. A new window can broadcast following shortly before it finishes becoming the stream owner, so only an explicit `no-client-found` response is retried for up to 10 seconds; timeouts and ambiguous errors are never retried to avoid duplicate turns. No second `thread-owner-discovery` round trip is used in this creation path. The independent App Server never calls `turn/start`; this prevents a background transport from consuming the live reply while the foreground page stays empty. The configured KSF root is used for both task creation and the submitted turn, so the task belongs to the saved Codex Desktop KSF project. The compact bootstrap input contains only the selected project name and memory-card path plus the key boundary: use KSF's normal rules to prepare base context, do no concrete work, change no files, produce no implementation plan, report readiness briefly, and wait for the user's next instruction. It does not duplicate Git mappings or KSF routing rules.
- Git engineering mappings never replace the KSF owner root. The new-task control is therefore always a direct action for no-Git, single-Git, and multi-Git projects; multi-root selection remains only on Git-folder and launch-action controls.
- The bootstrap turn inherits the visible task's thread settings and does not send approval, sandbox, model, or reasoning overrides. The user's normal Codex defaults therefore remain available after the preparation turn.
- The bootstrap prompt and returned raw thread ID are never written to app cache, UserDefaults, or logs. The prompt exists in the user-created Codex task by design. A missing directory or context entry blocks creation locally; a preparation or open failure stays in that project container, and no Shell fallback is used.
- `KSF` opens the selected KSF project directory. `Git 工程` opens its mapped engineering root in Finder. A single mapping opens immediately; multiple mappings use a menu with the exact active-task `cwd` match first.
- Each Git root may contain a current-user-owned, non-group/world-writable regular file named `codex-usage-bar.actions.json` with protocol `codex-usage-bar-actions-v1`.
- Each action has `id`, `title`, optional SF Symbol, `primary`, `executable`, argument array, and relative working directory. The resolved working directory must stay inside its engineering root. Control characters, duplicate IDs, traversal, damaged JSON, and incompatible versions are rejected.
- Show at most three primary actions at home and all actions in project details. Only a user click launches an action. It opens Terminal, runs the structured command in the declared directory, reports its exit status, and leaves output visible.
- Never auto-discover scripts, start them in the background, or accept environment variables/secrets in the manifest.

## Interface

- Keep the status label and global task-count rules from v0.1 unchanged.
- The popover is 336pt wide. Home scrolls only inside the bounded project region when included task content exceeds about 360pt or when `更多` adds projects. The complete project catalog has its own bounded continuous scroll region with stable content width. Project detail and settings contain no scroll view, tab view, or sidebar.
- Home order: header, general quota, account/local Token activity, then the KSF project heading and vertical project containers.
- Each project container shows its name, aggregate task status, every real active task, project lifetime/today Token, new-task shortcut, folders, complete details, and declared launch actions. Stage and focus remain in project detail rather than the home container. The running `play.fill` count is always present, including `0`; the pin icon alone conveys pinned state and `已固定` never replaces the running count.
- Every task row is a two-line full-width button. Line one contains status symbol, original name, explicit state, and chevron; line two contains that task's compact KSF route. Clicking opens `codex://threads/{percent-encoded-task-id}`. A local open failure appears only in that project container and never falls back to Shell or conversation inspection.
- The first four projects are included by default, with all their tasks. If their natural content exceeds about 360pt, the project region alone scrolls. `更多` includes projects beyond four in the same bounded region. A fixed trailing gutter prevents the scroll indicator from changing Cell width.
- The complete project catalog remains compact: project name, aggregate state or availability, navigation, and pin only. It does not repeat task names, task routes, Token metrics, or quick actions.
- Settings adds KSF directory status/reselection to login launch, quota-reset notifications, and the icon-plus-`退出` destructive action. There is no refresh button; opening, wake, and existing timers refresh data.
- Failures stay local to their region. KSF or project metadata failures do not change quota/task availability; quota failures do not remove the project catalog.

## Acceptance

- The live KSF export returns 15 current active projects, including no-Git, single-Git, and multi-Git cases, without the app parsing project Markdown.
- The current verified task appears under its bound KSF project even when its `cwd` is the KSF root; an unrelated KSF-root task without projection does not.
- Multiple running and waiting tasks under one project retain their own names, waiting reasons, and KSF routes; duplicate desktop windows do not duplicate rows or counts. Newly arriving tasks append without reordering existing rows.
- Project switching, stable pinned-first ordering, activity updates without row movement, unavailable pins, exact `cwd`, child inheritance, binding transitions, day boundaries, and missing logs are covered by deterministic tests.
- Action validation covers a valid manifest, traversal, unsafe permissions, duplicate/damaged fields, and visible Terminal execution failures.
- New-task tests verify `thread/start → thread/name/set → open exact task → matching following broadcast → targeted thread-follower-start-turn`, that the desktop turn request is sent only after the target window follows the task and is addressed to that same client ID, explicit task naming, KSF-root ownership regardless of zero/one/multiple Git mappings, compact verbatim bootstrap input without repeated Git context, inherited thread settings without approval/sandbox/model overrides, invalid-path rejection, IPC rejection handling, and the read-only stop boundary for automatic refreshes.
- The default home includes at most four projects but never truncates their task rows; only the project region scrolls when its content exceeds about 360pt. `更多` includes the remaining pinned/current-task projects. The complete catalog contains every project on one scrollable secondary page, has no pagination controls, and preserves identical row width with or without an indicator.
- Application Support contains no raw task ID, task title, prompt, conversation content, full route receipt, credential, or raw JSONL event.
- Direct tests, release arm64 build, Info.plist validation, ad-hoc signature, live App Server read, desktop IPC probe, and installed-app launch all pass.
